# Story Development｜先把原题讲好，再决定哪里需要加东西

这份文件只负责 `STORY_DRAFT`。目标是避免两个极端：

- Topic 已经有一个好核心，Production 又为“升级”发明第二套主机制；
- 为了避免创新过头，反而把所有故事都写成安全模板。

正式故事仍要有自己的具体观看身份、事件惯性和 payoff；只是默认先用**最自然的 Baseline Story**证明它，而不是先追求更复杂。

## 1. 先读取并冻结 `PRESERVE_LIST`

从已锁 Topic / Handoff 中提取 2–4 个不能轻易丢掉的价值：

- 强入口 / 第一笔观看债；
- 人物为什么进入这件事；
- 核心异常 / 主要问题；
- 最值钱的视觉内容；
- 后续观看牵引；
- `INNOVATION_ANCHOR`（若有）。

旧 Handoff 没有 `INNOVATION_ANCHOR` 时，从题眼里内部提取一条最有辨识度、最值得保护的具体东西即可，不回 Topic 补格式。

`PRESERVE_LIST` 的用途是防止 Story 为了修一个弱点，把原本已经成立的部分一起换掉。

## 2. 先写 `BASELINE_STORY_SPINE`

问：

> **如果不追求聪明，这个题最自然、最好懂、最像一个真正故事的完整路线是什么？**

Baseline 可以使用成熟 story grammar：失踪事件被新证据重启、现实任务逐步进入未知、近身威胁持续逼近、单线调查接近具体真相、私人线索驱动寻找公共未知等都合法。

先保证：

- 人物为什么继续自然；
- 第一层以后事情会自己往前推；
- 中段不是规则演示；
- 中后段至少有一次实质升级；
- 最后能把 MAIN_VIEWING_PULL 具体兑现。

不要因为 spine 熟悉就自动继续创新。

## 3. 用户要求参考 benchmark 时，先筛“学习价值”

只有用户明确要求参考 / 学习 / 对标作品，或本项目已明确把某作品集作为正式生产基准时，benchmark 才参与 Story 构建。若材料当前不可访问，不凭记忆补具体内容。

对可能适配的样本内部判断：

- `CRAFT_VALUE`：入口、人物继续理由、中段惯性、节奏、payoff 是否真的好；
- `NOVELTY_VALUE`：它的新鲜点是真正创意还是只靠包装；
- `TRANSFERABILITY`：经验脱离原人物 / 原场景后是否还能使用；
- `SIGNATURE_RISK`：借了以后是否容易变成原作换皮。

使用原则：

- craft 高、transferability 高：可学习 story spine / story inertia / payoff function；
- craft 高、novelty 普通：只学叙事效率，不模仿普通表面创意；
- novelty 高、craft 弱：只当启发，不把完整故事路线当范本；
- 学习价值低：不因为数据高就模仿。

## 4. Benchmark 可以帮“选路 / 修弱段”，不能替 Story 重写整篇

允许学习：

- 入口功能；
- 人物为什么自然继续；
- story spine；
- 中段如何保持 story inertia；
- 何时确认 / 何时升级；
- payoff function；
- 情绪变轨；
- 图片承担证据、距离、尺度还是结果。

需要重新设计后才能借：

- 人物关系类型；
- 场景类别；
- 证据介质；
- 异常载体；
- 终局类型。

继续禁止：原人物、原地点、标志物 / 怪物 / 场面、独特异常实现、可逐段映射的 beat chain、反转链、原结局和高度识别表达。

不要让同一篇 benchmark 从开头一路决定到结尾。

## 5. `WEAK_LINK_DIAGNOSIS`｜先指出哪里真弱

Baseline 写完后只问：**现在最影响观看的一个问题是什么？**

常见类别：

- `ENTRY`：开头没有债务；
- `MOTIVATION`：人物像为了剧情行动；
- `INERTIA`：中段会散 / 只剩重复证据；
- `ESCALATION`：后面没有真正发生到更高一层；
- `PAYOFF`：最后回报比前面承诺轻；
- `CLARITY`：事实 / 因果太需要猜；
- `IDENTITY`：题眼换名词就一样，缺少自己的具体身份；
- `NONE`：Baseline 已经成立。

`WEAK_LINK = NONE` 时停止结构创新，直接完善正式 Story。

## 6. `PRESERVE → REPAIR → RECONSIDER → REBUILD`

### PRESERVE

明确哪些内容继续锁住，尤其是 `INNOVATION_ANCHOR`、强入口和自然人物动机。

### REPAIR

只修当前 `WEAK_LINK`。例如：

- 中段散：让原异常真正造成后果 / 逼近 / 改变选择，而不是新加一个怪物；
- payoff 弱：让前面欠下的东西真正发生到顶，不自动开新世界；
- motivation 假：补现实原因 / 被迫条件，不用复杂设定救；
- 第二层普通：只重做第二层含义或下一事件，保住第一层。

有 benchmark 时，只调用与这个弱点匹配的成熟 grammar。

### RECONSIDER

局部修复后重新完整读一遍。已经达到高标准就停。

### REBUILD

只有局部修复仍无法解决核心结构时才重构，例如：题目天然没有后续、入口本身无欲望、最值钱内容无法通过图片兑现、所有路线都只能机制演示。

重构也优先保留仍然有价值的 `PRESERVE_LIST`，不要全盘清零。

## 7. Production 不欠作品“第二个主创新”

如果 Topic 已有明确 `INNOVATION_ANCHOR`，Production 的首要任务是把它变成完整故事。

出现以下情况时停止加机制：

- baseline 已经能自然推进；
- 同一威胁 / 调查 / 探索本身足够支撑中段；
- payoff 能从已有核心直接长出来；
- 新机制只会增加解释成本，没有增加更强观看欲望。

高风险信号：

- 为了中段“升级”突然增加隐藏世界、实验室、幕后组织；
- 为了显得原创强加时间循环、空间映射、身份反转；
- 每段引入一个新规则；
- 人物现实动机逐渐被作者的机制展示取代；
- 结尾只剩抽象的“同化 / 重构 / 被收录 / 现实改变”。

这些元素本身不禁用；只有当它们确实比原有简单路线更强、并能自然从前文长出时才采用。

## 8. 防止反向过度保守

成熟 story grammar 只是工具，不是模板配额。

如果一个新的高概念方向同时做到：

- 入口不受损；
- 人物继续更自然；
- 中段更有事件价值；
- payoff 更具体；
- 理解成本仍然可控；
- 不依赖 benchmark 指纹；

它完全可以胜过 Baseline。

不要因为本轮强调“简单 / 成熟”就自动选择最安全的版本。

## 9. 正式提交 Story 前的内部记录

只在内部保留：

- `PRESERVE_LIST`
- `INNOVATION_ANCHOR`
- `BASELINE_STORY_SPINE`
- `WEAK_LINK`
- `BENCHMARK_HELP = NONE / <只写借了哪类 grammar>`
- `REPAIR_SCOPE`
- `NOVELTY_STOP = YES / NO`

不需要把这些字段全部展示给用户。用户看到的仍是一篇自然完整的正式 Story。
